# CatLeaf：开源复评与 Android 路线决策

日期：2026-09-22。依据：GitHub 默认分支源码、依赖清单、README、发布元数据及 Android 官方文档。没有安装这些竞品做横向真机测评；下文“适合”是需求匹配判断，不是性能排行榜。首次调研保留在 [01](./01-开源项目调研.md)，当前决策见 [ADR 002](./decisions/002-Android原生客户端.md)。

## 1. 结论与前提

在“Android 优先、个人使用、保留猫页设计和 AI 功能、不以控制投入为首要目标”的前提下，推荐 **Kotlin + Jetpack Compose 原生客户端 + 原项目 Cloudflare 后端**。文章正文使用经过净化的受控 WebView；列表、导航、设置和数据管理使用 Compose。这不是直接把某个竞品改名，也不是将整个网站继续嵌入 App。

原项目仍适合作为后端与 AI 协议参考，但其 React UI 不再是手机主界面的运行底座。Read You、Capy Reader、Feeder 更适合参考 Android 阅读体验；Folo 更适合参考内容与 AI 交互。没有证据表明换框架即可自动达到流畅、可靠或安全，最终仍须通过现有真机验收。

如果用户只想立即使用现成阅读器，先试 Read You 或 Capy 更省事；但用户当前要的是带指定品牌、单源日摘要、自己的 API 和离线规则的 CatLeaf，因此直接换一个成品并不能完成既定目标。

## 3. 为什么仍选 Kotlin + Compose

| 方案 | 能胜任什么 | 对本项目的判断 |
| --- | --- | --- |
| Kotlin + Compose | 直接管理 Android 返回栈、生命周期、字体缩放、无障碍和本地数据库；正文可嵌入 WebView | **当前首选**。单平台目标明确，已有界面设计可落地，不需为跨平台维护适配层；代价是重写客户端与重新测试 |
| React Native + Expo | React 体系跨 Android/iOS，Folo 是实际阅读器案例 | 同样可做好；若近期明确 iOS 或以 React 团队交付能力为核心，值得重新评估。现在没有这一约束，不能只为复用 TS 就假定原 Web UI 可直接搬用 |
| Flutter | 自绘 UI、一套代码跨平台；Fluent Reader Lite 是参考 | 适合要求双端一致视觉的产品；本次单 Android 没有足够理由承担另一套运行时和平台适配。不能据此称 Flutter 性能差 |
| Capacitor | 最大限度保留 Web UI，增量接入设备能力 | 原先“尽快二开、控制投入”的合理方案，目前已有可运行基线。新优先级下不再作为最终客户端；WebView 本身不是缺陷，具体体验须实测 |
| uni-app / uni-app x | 分别有不同的跨端运行与渲染方式，适合已有 Vue/多端生态的团队 | 本项目是 React 上游且不做小程序，无法直接复用现有页面；不把两种产品混为“都是网页套壳”。没有选择它们的明确产品收益 |

选择 Room 是 CatLeaf 的工程决策，**不是“所有原生阅读器都用 Room”**。Capy 的 SQLDelight 同样是可行方案；本项目采用 Android 官方数据栈，减少维护两种数据库方案的必要性。[Room 官方说明](https://developer.android.com/training/data-storage/room)

文章 HTML 自带段落、图片、表格、引用与链接。受控 WebView 能保留这些语义；Compose 负责外层操作。Capy 和 Folo 均有这一组合的实际源码。CatLeaf 的实现应关闭 JavaScript/原生 JS 桥接、净化 HTML、限制资源与外链，而不是复制竞品 WebView 的全部权限。[Android 本地内容加载](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content)、[原生桥接风险](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)

## 4. 为什么不直接 fork Read You / Capy

二者的成熟阅读能力可减少基础工作，但接入成本必须结合差异看：猫页已有自己的 `/api/*`、单实例本地状态、手动 AI 和定稿设计。换整套客户端还要处理它们的账户/同步/服务适配与既有数据模型，并不等于只换 Logo、加一个摘要按钮。

本次选择一个单 app 模块的独立 Compose 客户端，直接实现已经冻结的 P0；复用 Android 标准能力和适当依赖，不从零写数据库、HTTP 或 HTML 引擎。避免预建多后端接口工厂、KMP、同步引擎和大型组件库。若实施时发现某个可独立复用组件明显减少工作，先核对兼容性及其许可，再记录采用依据。

Read You、Capy、Feeder 是 GPL；Folo/FreshRSS 是 AGPL，Folo README 对 `icons/mgc` 另有不可再分发说明。GPL/AGPL 并非“不能用”，但复制/分发源码与资源需按具体许可处理。这里采用行为参考、独立实现；不复制它们的品牌与图标。已有 gemini-rss-app MIT 和 Lucide 许可继续保留。

## 5. 已有成果与修改影响

- D01–D03、T01 保留完成记录。T02 和 G0 是旧 Capacitor 路线的模拟器验证成果，不能改名成原生验证。
- 旧 `android/`、React 源码、APK、截图及未提交修改保留。原生客户端拟建于 `android-native/`；不在原目录直接覆盖。开发 applicationId 使用 `dev.local.catleaf.nativeapp` 与旧 `dev.local.catweb` 区分；正式包名/签名按 T24 固定。
- 后端 T03/T06/T07 的改动继续复用，状态只按实际验收更新。已观察到后端未提交修改，不替实施 AI宣布通过、不回退它们。
- 新增 N01 原生工程与打包任务、G0-N 关卡；T04/T05 和后续界面改为原生实现落点。旧 G0 的约 9 秒首屏空白属于该包的缺陷观察，不能当框架横评；新包仍按 Release 性能目标测量。
- 22 张原型、52 个 SVG、暖白森林绿、A 歪头小叶猫保持；已有 VectorDrawable 可核对后复用。UI 图标按 SVG 转原生资源，React 组件名只作语义对照。
- 不承诺把旧 WebView/IndexedDB 自动迁入 Room。旧包不卸载；若已有用户真实数据，先盘点并安全导出，另行记录兼容迁移步骤，不用测试数据冒充迁移成功。
- 原 15–25 日估算撤回；N01/G1 后根据原生实现和实施 AI 的实绩重估。投入不限不等于无限扩张：跨源简报、通知、同步、iOS 仍为 P1。
