### N01：获取全文、标题重复与封面缺失

**当前实际流程**：

1. 打开文章时先读本地已有的 RSS/提取正文；主动保存的离线副本优先按其冻结内容读取。
2. 用户点击「获取全文」后，手机通过公开、无 App 凭据的 HTTP 通道获取原网页 HTML，最大 5MiB、仅 HTTPS、逐跳校验。
3. 手机抓取失败时，只有当前处于已连接的实例范围，才请求自有后端 `/api/article/extract?mode=raw` 获取 HTML。本机范围不使用该兜底。
4. 在手机侧用 Readability4J 1.0.8 提取正文，再经统一 jsoup allowlist 净化。
5. 本地写盘成功后，用提取结果替换当前正文；失败保留原正文。**这个操作不调用 AI。**

补充：当前后端兜底只在 HTML 抓取失败时触发；直连拿到 HTML、但 Readability 解析失败时，代码不会再请求后端。后端目前同样返回原始 HTML，不能承诺它会修复站点正文识别问题。

**标题重复已复现**：

- [原站样本 1682644](https://www.ifanr.com/1682644) 的 Readability 结果保留一个同名 `<h1>`。
- ReaderScreen 又通过 `readerHeaderHtml()` 添加 App 自己的同名 `<h1 class="catleaf-title">`。
- 净化器允许 `h1`，不会判断它是不是页首重复标题。因此实际呈现两个标题，正文内标题的默认上边距还扩大了空白。
- 用项目已缓存的相同 Readability4J/jsoup 版本运行公开样本，得到 `h1Count=1`、`byline=发邮件 莫崇宇`，与图一相符。证据：[探针输出](./validation/2026-09-30-feedback-assessment/readability-check.txt)、[可复现探针](./validation/2026-09-30-feedback-assessment/FulltextProbe.java)。

**封面缺失有两处缺口**：

- 爱范儿该条 RSS 将封面放在 item 下的 `<image>URL</image>`。当前 FeedParser 识别 media content/thumbnail 和图片 enclosure，没有识别这个条目级字段。
- 原网页已有 `og:image`、Twitter 图片和页首大图，但 FullTextExtractor 的结果只有 html/title/byline/fromBackend，没有单独提取封面。保存提取结果时仅保留旧 thumbnail，无法补回缺失封面。样本的页首封面不在 Readability 提取片段开头。
- 现有封面去重是 `bodyHtml.contains(thumbnail)` 的字符串判断，不区分它是正文第一张图还是中途图片，也不能可靠识别原图与 `!720` 变体的关系。

**同时确认的两项附属问题**：

- 作者栏混入操作文案：Readability 把「发邮件」识别为署名的一部分。RSS 实际 creator 为「莫崇宇」，但当前 Room 文章身份没有作者字段，不应假称作者已可直接从数据库回退。本次建议先保守清理明确的邮件操作前缀，不为这一点单独扩数据库。
- 列表摘要重复标题：DAO 用 `substr(COALESCE(c.content, c.summary), 1, 600)` 优先取正文；提取正文头部的同名 h1 被剥标签后又成为摘要开头。当前公开 RSS description 本身不以同标题开头。对同名开头标题的结构化去重应发生在保存/显示正文的共同处理位置，不能只用 CSS 隐藏。

**建议**：保留 App 页首标题；只移除正文开头、规范化后与当前文章标题或提取标题相同的重复标题，保留正常章节标题。补认 RSS 条目封面，提取全文时从已经抓到的网页读取封面候选并安全校验，使用现有 thumbnail 字段保存。选定封面在页首出现一次，移动/去重时保留合理图注和正文图片；无可靠封面就自然省略，不将任意正文截图冒充封面。正文更新后，重开文章仍应正确，不能只在本次会话有效。

主要源码：[FullTextExtractor](../android-native/app/src/main/java/dev/local/catleaf/nativeapp/data/article/FullTextExtractor.kt)（extract/fetchHtml）、[FeedParser](../android-native/app/src/main/java/dev/local/catleaf/nativeapp/data/rss/FeedParser.kt)（条目字段）、[ReaderViewModel](../android-native/app/src/main/java/dev/local/catleaf/nativeapp/ui/reader/ReaderViewModel.kt)（readerCoverUrl/fetchFullText/saveExtracted）、[ReaderScreen](../android-native/app/src/main/java/dev/local/catleaf/nativeapp/ui/reader/ReaderScreen.kt)（readerHeaderHtml）、[Daos](../android-native/app/src/main/java/dev/local/catleaf/nativeapp/data/local/Daos.kt)（listByFeedWithPreview）。

### N02：RSS 图片失败，提取全文后可显示

**该截图样本的主要原因已确认是单图大小上限，而非仅凭截图猜测防盗链**。

- 图二正文对应 [原站样本 1682571](https://www.ifanr.com/1682571)。RSS 使用原图 `.png`，原网页使用同站提供的 `.png!720` 版本。
- 对截图附近的 `lark2pad-1790727391335-2.png` 做限额 GET：原图 HTTP200、PNG、声明 **2,471,011 bytes**，超过现有 **2,097,152 bytes（2MiB）** 上限；网页版本 HTTP200、PNG、**667,749 bytes**，低于上限。
- PublicFetch 会将超限响应判为 TooLarge；ArticleBodyWebViewClient 将全部抓取错误统一变为「图片无法加载」。全文提取后 HTML 内地址换成网页的较小版本，就能通过现有通道。
- 第一篇标题重复样本中另外有 6 张 RSS 原图超过 2MiB，其 `!720` 版本均小于上限。说明这并非单次偶发连接失败。

证据：[图二对应图片的限额 GET](./validation/2026-09-30-feedback-assessment/image-feedback-bounded-get.json)、[第一篇 60 个图片地址的 HEAD 检查](./validation/2026-09-30-feedback-assessment/image-size-check.json)、[RSS/网页 DOM 对照](./validation/2026-09-30-feedback-assessment/ifanr-1682644-dom-comparison.json)。图片只测响应和限额，不保存远程图片文件。

**现有能力与待验证边界**：懒加载的 data-src、data-original、srcset/picture 回填已经存在，不再重复造一套。它仍优先保留非空 src，所以真实占位 URL 与更合适候选的选择需要结合样本完善。403、超时、异常 MIME 等其他站点失败原因尚未逐源证明，不能宣称所有图片问题均为大小造成。

**最终批准方案（2026-09-30）**：按用户要求将共用单图上限提高到10MiB（10,485,760 bytes），覆盖阅读正文、列表缩略图、主动离线保存和失败重试。上述2,471,011-byte原图可被新上限接收；第一篇抽查的30张原图最大2,571,591 bytes，6张超过2MiB，均未超过新上限。前文2MiB测量是历史故障证据，不改写为新版测试通过。

最小实施只调整现有`PublicFetch.MAX_IMAGE_BYTES`和离线说明文案，保留所有调用者共用常量；此次不需要新建CDN改写或图片身份映射。单篇20MiB/50图、总300MiB预算、HTTPS、无凭据、逐跳验证、类型检查、缩略图采样和旧包保护保持。新上限不能解决403、超时或无效URL，压缩文件大小也不等于解码后的内存占用。

实施与边界检查见[IP01](../tasks/本机模式与发现源实施计划.md)、[PRD§11.3](./03-PRD.md)、[契约§3.3/9.2](./04-架构与接口契约.md)、[补充验收](./06-验收与发布.md)。当前源码常量和code6安装包仍为2MiB；本轮仅同步批准的产品限额及开发任务，真机改后验证待执行。此前保留2MiB并改CDN候选及随后5MiB的方案均由10MiB替代；HTML抓取仍为5MiB，不混同单图限额。

### N03：关闭状态出现粉紫色

**根因确认**：阅读与搜索开关都走共享 ToggleRow，内部 Switch 没有显式 colors。应用主题已覆盖 surfaceContainer/Low/High，却漏了 `surfaceContainerHighest`。Material Switch 的未选中轨道使用这一颜色 token，留下默认粉紫色。

项目实际依赖 material3-android 1.4.0，缓存类文件包含相应 token；官方 [SwitchTokens 源码](https://github.com/androidx/androidx/blob/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/SwitchTokens.kt) 及 [SwitchDefaults 文档](https://developer.android.com/reference/kotlin/androidx/compose/material3/SwitchDefaults) 同样说明开/关/禁用轨道等颜色分别由主题或显式参数决定。这是主题映射漏项，不是 RSS 内容或 Android 系统主题造成。

**建议**：首先补齐浅/深主题中实际使用的该 token 为已有中性表面色，再核对共享 ToggleRow 的开启、关闭、禁用开启、禁用关闭及轮廓对比度。仅必要时在共享控件中明确覆盖颜色，不逐页写补丁，也不改成另一种控件。

源码：[Theme](../android-native/app/src/main/java/dev/local/catleaf/nativeapp/ui/theme/Theme.kt)、[Controls](../android-native/app/src/main/java/dev/local/catleaf/nativeapp/ui/theme/Controls.kt)（ToggleRow）。

### N06：调查中额外发现的正文/翻译状态不同步

**源码已确认，修复后真实行为待验证**：ReaderViewModel 打开文章时初始化 `currentPlainText` 和 `translatableChars`。获取全文成功后仅更新 bodyHtml/bodyPreview/bodyHash等，没有同步这两项，也没有按新正文重置/重查已展示的旧译文。后续翻译请求及缓存键仍取 `currentPlainText`。

结果风险：同一会话中画面显示提取全文，但翻译输入、字数和缓存匹配仍按旧 RSS 正文，违反「翻译当前已展示正文」契约。重新打开文章时会重新读取已保存全文，因此不能只以重开后的正常结果验收。

**建议**：与N01一起处理正文成功替换后的状态同步；在文章/范围仍匹配、写盘成功之后更新纯文本和字数，重新按新输入判断译文缓存，失配旧译文不当作当前正文结果展示，不自动调用AI。用本地假响应/缓存即可验证输入和缓存键，不需用户先提供真实Key。真实收费AI结果仍保留在原G7待验证项。
