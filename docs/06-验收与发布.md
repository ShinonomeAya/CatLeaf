## 1. 环境与证据要求

至少覆盖用户实际 Android 手机，以及第二台真机或一个模拟器。产品支持目标 Android 10+；至少检查 Android 10 的最低目标与实际常用系统版本。记录机型、Android/WebView 版本、内存、网络类型、App 版本/源码 SHA、Kotlin/Compose/Room/Gradle 版本和后端部署标识，不能只写“安卓已测”。

测试数据最少含：一个 RSS 2.0、一个 Atom；带全文和仅摘要的文章；GUID 缺失、重复 link、两个标识都缺失；不同 UTC 偏移和无效日期；中英混排、长标题、长正文；失效源、含重复和多级分组的 OPML；恶意 HTML/URL。优先自己生成固定小样本以保证可重复，真实可用源另外验证，不依赖作者隐藏目录。

自动化检查用虚构凭据/可控响应；真实 AI 只做必要连通与质量验收，避免重复付费。手动记录至少含步骤、预期、实际、截图/日志路径和结论。日志、截图、导出样本不能包含用户的真实 Key 或私有 URL token。

## 2. 三层检查

| 层次 | 主要内容 | 能证明什么 / 不能代替什么 |
| --- | --- | --- |
| 纯逻辑可重跑检查 | 文章身份、日期边界、URL/OPML、AI 缓存键与来源编号、状态合并 | 证明规则；不能证明Room/Keystore 的实际设备行为、系统返回与真实网络 |
| 本地 API / D1 检查 | 认证、HTTP 方法、私有缓存、输入限额、分页/去重、抓取失败 | 证明 handler 集成；不能证明线上绑定和地域可达 |
| Android 真机与线上验证 | 本地资源启动、密钥/SQLite、离线、分享、升级、实际 RSS/AI | 证明用户环境；不能由浏览器截图或 mock 取代 |

上游已存在可核对的命令：`npm ci`、`npm run lint`、`npm run typecheck`、`npm run build`、`npm run preview:cf`。上游基线没有测试脚本；`npm run test:core` 由 T21 建立或核对，实施时以实际 package.json 为准。该命令只覆盖后端逻辑，不能证明 Kotlin 客户端通过。基线错误单独记录，不给未运行的命令打勾。

N01 建立工程后，在 `android-native` 中用其 Gradle wrapper 执行 `./gradlew.bat :app:assembleDebug`、`:app:lintDebug`、`:app:testDebugUnitTest`；Room 迁移、Keystore/WebView 与必要 Compose 交互在设备执行 `:app:connectedDebugAndroidTest` 并补真实手动流程。若任务/构建变体名称实际不同，先核对再回写。工程与测试尚不存在时，不得记录这些命令通过；空测试套件也不是规则验证。

纯逻辑使用最少测试文件，复用已有工具链；无需为卡片文字、样式间距或纯转发包装写镜像测试。认证、解析、事务、防泄漏等非平凡逻辑必须留下能发现回归的检查。引入测试执行工具前先检查现有工具是否足够。

## 4. 性能、无障碍与缺陷判定

性能参考条件：指定一台实际手机，Release 构建，缓存有 200 篇常规文章；分别做 20 次冷启动和 20 次本地详情打开，记录每次耗时。冷启动从点击图标到缓存阅读界面可操作；详情从点击到缓存正文可读。先排序取第 19 个样本作为本次 20 样本 nearest-rank P95；不能报最快一次。目标启动 P95 ≤2.5 秒、详情 ≤1 秒；网络/图片耗时另外记录。目标未达则分析主要阻塞，不先加复杂性能框架。

360 dp 宽、系统字体放大、浅/深色、软键盘弹出均可用。TalkBack 至少走完选择源→打开文章→收藏→返回；主要目标至少 48 dp，焦点顺序与标签可理解。不要只用颜色区分错误/已读。T22 同时依据 [设计规范](./07-设计规范.md) 和 [页面原型](./prototypes/README.md) 核对层级、色彩、导航和状态；不将设备外框、示例内容或生成图片的像素误当实际 UI 要求。

| 等级 | 示例 | 发布处理 |
| --- | --- | --- |
| 阻断 | Key 泄露、未授权读写、正文执行脚本、收藏/状态丢失、无法安装启动、升级删库 | 必须修复并复验，不交付为可日常使用版 |
| 主要 | 首版流程不可完成、AI 重复自动计费、OPML 重复覆盖、正文离线不可读、来源伪造 | 必须修复；取消功能属于范围变更，不能静默降级 |
| 一般 | 不阻断阅读的局部布局/文案问题 | 如实记录，可由用户接受为已知问题；不能伪称全部通过 |

缺少测试设备或账号不是“通过”，是待验收。性能目标未达需要说明实测差距和修正计划，不能在报告中偷换测试起止点。

## 5. 自有 Cloudflare 部署手册

本节供选择自有实例的用户使用，本机基础阅读无需部署；T23及实例能力验收继续有效。T05如需真实测试实例使用同一路径。只操作用户自己的资源。正式发布动作在代码、配置、回退步骤可审阅后，根据用户已有授权进行；不要每个可逆本地步骤都问许可。

| 配置 | 来源 | 保存位置/检查 |
| --- | --- | --- |
| Pages 项目名及 HTTPS origin | 用户自己的 Cloudflare 项目，可先用 pages.dev | 脱敏部署记录和 App 运行时配置 |
| `DB` | 用户 D1 数据库绑定 | wrangler/平台配置与代码一致；实际 database_id 非空且属于自己 |
| `RATE_LIMIT_KV` | 用户 KV namespace | 实际包装函数传入 env 绑定；绑定存在不等于代码使用 |
| `ADMIN_SECRET` | 用户本地生成高强度随机值 | Cloudflare secret、App 安全存储；不进入前端 VITE 变量或源码 |
| 文章/媒体大小限制 | wrangler 已有字段与契约约束 | 同时验证代码读取；不只改文档 |
| `DATABASE_URL` | Cloudflare 首版不需要 | 不填作者 Neon 配置，不为了兼容另建 PostgreSQL |

操作顺序：

1. 核对账号、项目和环境；测试资源与生产数据分开。先运行本地检查，确认路由保护已生效。
2. 创建/选择自己的 D1、KV、Pages，并配置绑定与 secret。上游 wrangler 中资源 ID 为空，不能当作可直接发布的配置；不提交 secret。以锁定 Wrangler 版本的官方文档为准。[Pages 绑定说明](https://developers.cloudflare.com/pages/functions/bindings/)
3. 将数据库名称与迁移脚本改为自己的实际目标。先本地迁移并检查，再针对正确远端执行迁移；仅 D1 schema 真有变化时生成新迁移。原脚本 `db:migrate:d1:local` / `db:migrate:d1:remote` 固定引用上游名字，未经核对不要直接对远端执行。
4. 构建并使用原 `deploy:cf` 路径发布到自己的项目；确保 Functions 随部署存在，不能只上传静态目录造成 API 404。绑定调整后按平台要求重新部署。
5. 从手机网络请求私有 API：无密钥 401、错密钥 401、正确密钥能读/写并 no-store；查看 RSS/Atom/提取/历史和 KV 真实行为，检查日志脱敏。
6. 输出部署时间、版本、origin、资源名称、迁移编号、检查结果和回退标识。不在此处记录 secret。

首版不搭建完整 CI/CD 平台。已有自动工作流仅在账号、目标和发布意图明确后启用；本地 `build` 不得触发云端修改。

### 备份与恢复

云端 D1、手机状态文件和 Android 签名材料是三类不同备份。D1 不含手机已读/收藏；状态文件不含正文、AI 缓存或 Key；签名材料不能放进普通用户数据导出。

升级/数据库变更前导出 D1。官方支持 `wrangler d1 export` 生成 SQL，再用 `d1 execute --file` 导入；实施时将命令中的数据库名称、远端标志和文件路径替换为已核对目标，先恢复到隔离数据库，校对源/历史数量与抽样正文，再考虑用于真实恢复。导出可能暂时影响数据库请求，选自己不用 App 的窗口。[D1 导入导出](https://developers.cloudflare.com/d1/best-practices/import-export-data/)

用户定期手动导出状态文件，在大批导入/清理/换手机前额外导出。首版不承诺自动备份；不要把计划中的手动步骤描述为已经配置的定时任务。

### 日常维护和费用

自用第一周每次出现问题时记录：哪个源/哪一步、网络、错误码、是否能读旧内容；不要先部署监控平台。用户可在 Cloudflare 和 AI 供应商面板检查请求量/存储/费用，按实际计划设置供应商支持的额度或提醒；KV 限流不是严格计费上限。月费在供应商、模型、阅读量确定后计算，不保证永久免费。

密钥疑似泄露时：轮换 Cloudflare secret 或供应商 Key → App 更新本地配置 → 验证旧 Key 失效 → 检查日志与额度。源失效优先确认原 URL/网站变化，不全量清缓存或重建数据库。

## 6. Android 打包与升级手册

1. G7 问题收口后复核正式显示名、包名、版本号、图标和签名。品牌与平台图标在 D01 设计、旧 T02 接入过；新工程 N01 核对复用并接入，不能等到发布前才开始准备；资源要求见 [素材交付](./08-素材交付与开发准入.md)。个人首版直接APK，不必开通应用商店；不复制作者品牌，保留源码与依赖许可。
2. 核对 N01 锁定的 Kotlin/Compose/Room/SDK/JDK/AGP/Gradle 组合。minSdk=29；compile/targetSdk 按当前兼容要求选择并实测最低系统和用户系统，不照搬旧 Capacitor 模板。
3. 先完成原生与后端各自检查，再构建 `android-native`；不执行 cap sync，不依赖 dist。检查主界面编译入 APK、正文模板本地可用；不含真实 Key、调试日志、明文 HTTP 豁免或关闭 TLS 校验。
4. 在用户保管的签名配置下，进入 `android-native` 目录运行 `./gradlew.bat :app:assembleRelease`。**assembleRelease 本身不证明已签名**，必须检查最终签名和可安装性；keystore、口令不能入库。签名丢失会影响后续同包名升级。[Android 签名说明](https://developer.android.com/studio/publish/app-signing)
5. 确认实际输出文件路径，计算 SHA-256，记 versionName/versionCode、包名、签名证书指纹。不要在未产出前提供猜测的下载路径。
6. 在隔离环境验证新装，在用户手机以同签名、更高versionCode覆盖升级，检查订阅、已读、收藏、配置和读位；不为测试卸载现有包。新开发包与旧Capacitor包并存，旧包不自动迁移/卸载。原实例用户保留原使用方式，不强制迁移或重走引导。T24不能用卸载重装冒充保数据升级。
7. 新装不配置实例和AI走订阅→阅读→收藏→飞行模式重启；另验可选实例与AI路径。交付时说明必要安装操作，不要求关闭设备安全保护。

Android 回退优先“旧功能代码 + 新 versionCode”的前向修复包，且必须兼容已升级的本地 schema；不能承诺直接装低版本 APK 并完整保留数据。后端可回退兼容的 Functions 部署，数据库迁移不能凭应用回滚自动撤销；先验证备份和旧代码兼容性，避免破坏性回滚。
