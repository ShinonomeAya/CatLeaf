# 翻译布局、全部订阅与生成源配置调查

日期：2026-10-09（Asia/Hong_Kong）。范围：用户新截图与三项调查要求；本轮只调查和规划，没有修改 App、重建 APK、操作手机或请求收费 AI。源码、目录和旧 APK 均重新核对；旧通过记录不能作为本批验收。

## 1. 翻译栏被挤成竖条

用户截图中的竖条是「重新翻译（会再次请求）」操作文字。正文译文仍横向显示；不能据此认定 AI 返回了竖排文字，也没有证据表明所有译文正文都有排版问题。

`ReaderScreen.kt:303–341` 在一个无自适应换行的 Row 内依次放两个 FilterChip、译文状态 Text 和 TextButton。Row 只有左右 20dp 内边距、8dp 间距，子项没有合理分配可用宽度。前面内容占满后，最后按钮被限制在很窄的空间，中文逐字换行；Row 高度由这个按钮撑高，其他子项又垂直居中，形成截图中的大片留白。这是与截图一致的源码定位，尚未在本轮设备上复现。

同一结构覆盖「刚刚生成」「已缓存」、原文/译文切换和重新翻译，不应只改某个状态文案。`ReaderViewModel.translate(force=true)` 会跳过缓存再次请求；普通查看已有译文不会再次请求。布局返修必须保留这个区别及费用提示、离线/在途禁用、失败保留内容、文章/范围/正文版本归属检查。

建议：拆成切换区和状态/操作区，使用自然换行；操作短文案「重新翻译」，「会再次请求，可能产生费用」单独说明。不缩字号、不截断费用提示、不设置死高度。以 360/411dp × 字号1.0/1.3 × 深浅八组实际截图检查，并用本地假译文/假请求确认触摸、切换、请求次数与失败保留。现有 `TranslationTypographyTest` 只验证正文随字号变大，不能证明工具栏宽度正确。

## 2. 是否需要「查看全部」

当前已经存在三种容易混淆的“全部”：

| 位置 | 现有行为 | 缺口 |
| --- | --- | --- |
| 阅读页订阅选择面板 | 按分组列出当前范围所有已订阅的源，点一个源显示该源文章 | 没有所有源文章的聚合阅读 |
| 发现页「全部」 | 浏览内置可发现目录 | 不等于用户已订阅，也不抓目录里全部文章 |
| 文章搜索「全部订阅」 | 搜索当前本机/实例范围所有已保存文章 | 需要关键词，不是聚合阅读首页 |

`ReadingViewModel.start()` 默认上次源/首源，`selectFeed(String)` 只选单源；仓储的加载、计数和历史接口都要求单个 feedId。仅在选择面板加按钮不会得到完整功能。

建议增加「全部订阅」聚合阅读选项，放在现有订阅选择面板首项；下面仍列出所有源，点击进入单源。复用阅读页、筛选、分页和源选择面板，不新增底部 Tab 或重复源列表页面。若用户仅想“查看所有订阅源名称”，已有面板足够，需改善可发现性即可。

建议首版语义：

- 只聚合活动本机/实例范围内、当前仍订阅的源的已保存文章，不混入其他范围或已删除源残留身份；收藏/主动离线副本继续独立保护。
- 按时间倒序、未知时间最后、稳定文章ID破同序；不同订阅的同篇文章不额外引入跨源去重规则。聚合行增加源名称以便辨认。
- 查询数据库分页，保留200篇后的继续加载；筛选须在取页时正确参与，不能让前200篇不匹配造成假空态。单源原路径继续回归。
- 先显示缓存；前台按既有过期规则逐源刷新，手动刷新顺序处理当前范围源，显示进度与失败源，失败保留各源旧内容，禁止无限重试与后台常驻抓取。大范围刷新可停止，离开/换范围后结果不能覆盖新列表。
- 聚合页「加载更多」只承诺本机已保存页；实例尚未下载的历史继续在单源读取，不偷偷循环抓完所有源历史。
- 用明确的聚合选择状态区分“全部”和“没有源”；保存选择/锚点时带范围，旧上次单源设置兼容。不能把虚构feedId传给RSS或实例API。
- 搜索从聚合页带入全部订阅；日摘要仍为单源，聚合态提示先选一个源，不扩成多源收费AI。
- 第一版保持既有默认源，不强行将所有用户启动页改成聚合；用户主动选择后记住。实际实施前同步PRD/契约/页面说明的增量语义。

## 3. 「需要配置」到底配置什么

本轮重算 APK 资产：目录版本 `2026-09-27.3`，303项；78项 `ok`，225项 `needs_config`。225项实际为 RSSHub 30、Anyfeeder 192、FeedBurner 3。`tools/catalog/verify-catalog.mjs` 按第三方主机识别后统一标记需要配置，而非逐路由证明需要账号。**因此不能把225项解释成225项必须登录。**这些数量是本轮本地资产检查，不是225条在线可用性复验。

| 类型 | 实际配置位置 | 猫页读取方式 |
| --- | --- | --- |
| 官方公开RSS/Atom | 通常只需最终订阅地址 | 手动添加/发现添加并验证 |
| 公开RSSHub路由 | 生成服务的HTTPS域名 + 文档路由 + 必需的公开ID参数 | 在生成服务验证XML后，将完整RSS地址加入猫页 |
| 需要登录/Token的生成路由 | 用户自有生成服务的环境变量或后台；不是猫页AI设置 | 生成服务持有登录态，猫页消费符合当前安全约束的输出RSS |
| Anyfeeder等托管生成源 | 先核实服务状态与该源实际要求 | 可公开读取时并不要求自建；不能把Anyfeeder路径原样换成RSSHub域名 |
| FeedBurner分发地址 | 核查原RSS/分发URL与HTTPS可读性 | 不应仅因域名是第三方就要求用户自建RSSHub |

RSSHub官方文档说明路由由实例域名、路径和参数构成，配置通过环境变量设置；账号要求应以具体路由为准。例如当前微博用户路由声明Cookie可选，但说明部分账号只有登录后可见。[RSSHub入门源码](https://github.com/RSSNext/rsshub-docs/blob/main/src/zh/guide/index.md)、[官方配置文档源码](https://github.com/RSSNext/rsshub-docs/blob/main/src/zh/deploy/config.md)、[微博路由源码](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/weibo/user.ts)。官方文档站本轮返回403，采用项目官方文档仓库与路由源码交叉核对，未把镜像/博客当权威。

无登录要求的示例过程（不实际部署）：在用户自己可用的HTTPS RSSHub服务，按官方示例使用 `/telegram/channel/awesomeRSSHub` 路由，得到 `https://用户自己的域名/telegram/channel/awesomeRSSHub`；验证其返回RSS，再在猫页手动添加。此处域名是说明占位符，不是承诺可直接使用的地址。必填ID按该路由文档填写；不自动把全部第三方URL批量换域名。

需登录源的过程：先在自己控制的生成服务登录或配置该路由要求的环境变量，验证登录有效和输出RSS；再将可供猫页读取的输出端点添加进App。Cookie、密码和主密钥仅留在生成服务的安全配置中，不写到发现资产、Room、普通OPML/状态导出、日志或聊天。

猫页的「连接自己的实例」指CatLeaf后端，**不等于配置RSSHub，也不会自动获得微信登录态**。当前公开抓取不带Cookie/Auth，仅HTTPS并阻止内网目标，所以普通NAS的HTTP/内网地址、需要Basic/Auth头或含密钥查询参数的私有RSS不能宣称直接兼容。RSSHub文档允许URL访问密钥，但本项目禁止凭据入URL；若要支持私有订阅认证，需另行设计独立凭据通道及导出/跳转保护，不用“把Key加到地址里”临时解决。

建议本批先完善条目说明：可公开读取、需提供生成地址/路由参数、生成服务需登录、待核验；复用现有条目note及添加表单。逐项核验后才更新资产，不把225项一键改为可用，不建设通用Cookie管理平台。

## 4. 微信公众号的列表、正文和图片要分开

### 获取文章列表

RSSHub当前有公众号首页栏目/话题等路线，但覆盖限定入口。主页栏目路由明确标为非推送/非历史消息，仅适用于提供首页模板的公众号；不是任意公众号全量订阅接口。[RSSHub公众号栏目源码](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/wechat/mp.ts)。

Wechat2RSS作者文档描述：私有生成服务需微信读书授权及扫码账号，服务产生订阅地址；账号登录异常或风控会阻止更新。因此登录发生在生成服务，手机阅读器只读取输出RSS。[作者使用指南](https://wechat2rss.xlab.app/deploy/guide)。

方案状态需考虑：WeWe RSS主仓库本轮显示2026-05-11已归档，不能作为持续维护默认方案；Wechat2RSS私有版为收费授权，作者页面限定个人学习研究、禁止商用和内容分发，不适合直接作为猫页公开托管抓取基础。本轮未购买/部署/扫码，也不对任何服务的长期可用性作保证。[WeWe RSS仓库](https://github.com/cooderl/wewe-rss)、[Wechat2RSS私有部署说明](https://wechat2rss.xlab.app/deploy/)。公开APK可以说明用户自选生成源的接入方法；集中托管或分发他人内容另行评估，不能由本轮调查自动启动。

### 已有公开文章的正文和图片

微信公众号图片失败不能一概推断为未登录，应逐层检查：

1. RSS是否真的包含正文/图片；原文章是否返回正常内容、验证页、删除/受限提示；HTTP200本身不代表正文成功。
2. 图片地址是否在 `data-src`，`src`是否空、data占位或非空HTTPS占位；清理后是否留下真实地址。RSSHub共享微信处理会用非空data-src替换src。[共享微信处理源码](https://github.com/DIYgod/RSSHub/blob/master/lib/utils/wechat-mp.ts)。
3. 真实图片HTTPS请求的状态、Content-Type、字节数和可解码性；分别检查直链与生成服务自己的图片端点，不能把HTML验证页当图片成功。
4. 来源Referer、失效图片端点/签名、网络/重定向、10MiB限制和离线预算；与在线正文、列表缩略图、主动保存和重试四条路径交叉比对。

猫页已有 `fillImageSources` 的data-src候选，也已有四类图片统一安全origin Referer。因此既不能再重复添加同样代码，也不能承诺“加Referer即可修复全部微信图片”。已确认候选缺口：非空、非data的src会提前返回，覆盖不到“HTTPS占位src + 真实data-src”。是否命中用户失败文章，仍需公开文章URL与订阅地址，不读取真实账号或凭据。

建议实际样本若证明命中：在已有共享净化中增加精确的微信图片候选规则，经现有安全校验后使用真实data-src；普通图片优先级不随意改变，不能全域盲目覆盖src。若只有已净化旧缓存且真实属性已丢失，不能凭空恢复地址，需要用户主动刷新/获取全文；不全库静默重写、不自动改旧离线包。

Wechat2RSS有生成服务自己的图片代理及HTTPS/外链配置；这是该生成服务提供的能力，不是猫页现有媒体代理。输出地址错误、HTTP图片、账号失效时要在服务端处理。签名图片URL与主密码不同，但其访问能力和保存/导出边界需核对，不能把RSS_TOKEN/RSS_PROXY_SECRET交给公开抓取。[作者配置说明](https://wechat2rss.xlab.app/deploy/config)。不新增公共CORS/媒体代理，不关闭TLS/SSRF校验，不把微信登录搬进正文WebView。
